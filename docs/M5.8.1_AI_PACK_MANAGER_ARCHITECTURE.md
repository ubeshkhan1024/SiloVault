# M5.8.1 — AI Pack Manager Architecture

> [!IMPORTANT]
> **Status (26 November 2026): design document, not delivered functionality.** `backend/ai/pack_manager.py` is a deliberately minimal, **read-only** foundation: it exposes pack capability/metadata/manifest models, hardware-compatibility checks, recommendations, and **in-memory** approval objects. It does **not** download artifacts, verify checksums, persist approvals, install packs, or provide any UI. Everything described below as a workflow, lifecycle or UI is a target design. Do not cite this document as evidence that secure downloading, checksum-verified installation or pack installation exists.
>
> Milestone numbering: "M5.8.1" belongs to the **AI model-runtime track** (AI-M5.x). It is unrelated to roadmap Milestone 5 (additional cloud providers).

## 1. Goals and Non-Goals

### Goals
- Design a modular architecture for optional, user-approved AI model pack installation.
- Ensure SiloVault remains fully functional without any AI packs installed.
- Provide hardware-aware model recommendations based on system capabilities.
- Design (not implement) secure, verified model downloads with checksum validation. **Only the recommendation half of this goal exists in code today.**
- Enable lazy model loading and efficient resource management.

### Non-Goals
- Bundling model weights with the core application.
- Automatic or mandatory AI inference.
- Cloud inference fallback.
- Implementing the installation service or UI in this milestone (this is architecture/design only).

## 2. Existing Architecture and Reusable Interfaces

The AI Pack Manager leverages the following existing foundations:
- **`ModelDescriptor`**: Defines model metadata, including `checksum`, `model_size_bytes`, `licensing`, and `supported_platforms`.
- **`CapabilityRegistry`**: Maps capabilities (e.g., `image_description`) to compatible `ModelDescriptor` entries based on the current profile (`Efficient`, `Balanced`).
- **`HardwareInfo` / `HardwareDetector`**: Provides system-level hardware snapshots (RAM, CPU, GPU/NPU) and profile recommendations.
- **`ModelStorage`**: Manages the local directory structure for model storage.
- **`ModelInstallationService`**: Handles the transactional installation of verified model artifacts from staging to the storage directory, including manifest validation.

## 3. Proposed Architecture

The AI Pack Manager acts as a high-level orchestrator that bridges user intent, hardware capabilities, and model availability.

### High-Level Workflow
1. **Discovery**: `CapabilityRegistry` identifies potential models for a desired capability.
2. **Hardware Matching**: `HardwareDetector` provides `HardwareInfo` to `CapabilityRegistry` to filter models by hardware constraints (e.g., RAM for Large-FT models).
3. **Recommendation**: The UI displays recommendations with verified metadata (size, license, hardware needs).
4. **Approval**: User provides explicit approval for the selected pack.
5. **Installation**: `ModelInstallationService` performs transactional installation.
6. **Runtime Management**: `VisionRuntimeManager` handles lazy loading/unloading of the model into the runtime.

## 4. Pack Manifest Example

Each model pack includes an `installation.json` manifest:

```json
{
  "schema_version": "2",
  "identifier": "microsoft.florence-2-base",
  "version": "1.0",
  "packaging": "single-file",
  "installed_at": "2026-11-23T02:00:00Z",
  "entry_point": "model.safetensors",
  "files": [
    {
      "path": "model.safetensors",
      "size": 931377580,
      "sha256": "..."
    }
  ],
  "source": {
    "type": "https",
    "url": "..."
  }
}
```

## 5. Hardware Recommendation Logic

The recommendation engine uses `CapabilityRegistry.resolve(capability, profile)` and filters by:
- **RAM**: Required for model footprint + runtime overhead.
- **Compute**: CPU/GPU capabilities declared in `ModelDescriptor.hardware_requirements`.
- **Storage**: `ModelDescriptor.model_size_bytes` vs. available disk.

## 6. Dependency-Sharing Strategy

- **Core Deps**: PyTorch/Transformers shared in the main application environment.
- **Pack-specific Deps**: Minimal; if extra dependencies are needed, they should be pre-validated by the installation service.

## 7. Installation Lifecycle

- **NOT_INSTALLED**
- **DOWNLOADING** (In-progress artifact transfer)
- **VERIFYING** (Checksum/size validation)
- **INSTALLING** (Atomic manifest publication)
- **INSTALLED**
- **FAILED** (Rollback required)
- **RECOVERY_REQUIRED** (Corrupted manifest/storage)

## 8. Runtime Lifecycle

- **UNLOADED**
- **LOADING**
- **READY**
- **EXECUTING**
- **ERROR**

## 9. Security and Privacy

- HTTPS only for all downloads.
- Mandatory checksum verification (SHA-256).
- No automatic cloud inference.
- Isolated storage directories.

## 10. UI Workflow

1. **Settings/AI**: Displays available capabilities.
2. **Discovery**: User selects capability (e.g., "Image Understanding").
3. **Recommendation**: System displays compatible models based on `HardwareDetector`.
4. **Review**: User reviews license, size, and compatibility.
5. **Action**: "Install Pack" button initiates verification/approval.

## 11. Integration Points

- `CapabilityRegistry`: Capability-to-model mapping.
- `VisionRuntimeManager`: Runtime lifecycle management.
- `ModelInstallationService`: File-system operations.

## 12. Limitations and Unresolved Questions

- UI design (cards vs. table) is undecided.
- Idle timeout for model unloading needs benchmarking.
- Manual model import (user-provided `.safetensors`) requires validation logic.
- Proactive vs. reactive recommendation logic.
